# C4-a 설계 — 방향별 damping의 대체 가능성

**상태**: 설계 + 재실행 0 파일럿 완료. 정식 결과가 아니라 방향 신호 확인 단계.
**출발점**: `Diff3R_논문정리.md`(팀 독서 노트, 2026-08-19)가 제기한 질문.

## 1. 질문

Diff3R(arXiv 2604.01030)는 per-Gaussian, per-attribute 정규화 가중치 Λ를 **학습**해 방향별
LM damping을 얻고, 비겹침(non-overlap) 영역에서 그 값이 커짐을 보인다(Fig. 5/6) — 즉
"어디를 세게 고정하고 어디를 자유롭게 둘지"를 학습으로 얻는다.

우리 질문: **그 방향별 damping이 반드시 학습되어야 하는가, 아니면 이미 나오는 신호(기성,
off-the-shelf)로도 같은 걸 볼 수 있는가?**

이미 확인한 제약: MVSplat/DepthSplat/FSGS 모두 기본 설정에서 실질적인 confidence 출력을
제공하지 않는다(FSGS의 `confidence` 필드는 상수 placeholder). 따라서 "confidence를 직접
대체"하는 게 아니라, **원래 다른 목적으로 학습된 출력이 우연히 그 역할을 대신할 수 있는가**를
본다.

## 2. 측정 설계

**측정 대상**: C1-b(§4.5, 동일 초기값 refinement on/off)의 체크포인트를 그대로 재사용한다.
refinement 전(iter0, feed-forward 원본 출력)과 refinement 후(60s) 사이 각 Gaussian의 위치
변화량을 "이동량"으로 정의하고, 이게 후보 대체 신호와 상관관계가 있는지 본다.

**후보 대체 신호** (구현 난이도 순):
1. **opacity** (이번 파일럿에서 실제로 씀) — feed-forward가 렌더링 손실만으로 학습하지만,
   깊이 경계·반투명·저겹침처럼 불확실한 지점에서 낮게 나올 개연성이 있다. 이미 체크포인트에
   저장돼 있어 추가 코드가 필요 없다.
2. **cost volume variance** (MVSplat/DepthSplat 전용, 코드 수정 필요) — plane-sweep cost
   volume의 depth-hypothesis 분포 peakiness. encoder 내부 텐서를 forward pass 중 추출해야
   한다.
3. **기하 기반 σ_depth** (이미 구현됨, `two_view_depth_uncertainty()`) — baseline/overlap에서
   나오는 이론적 깊이 불확실도(§5.1). Gaussian을 view-pair에 역매핑해야 하는데, MVSplat의
   per-pixel 예측 구조상 pixel index → view index는 알 수 있지만 view-pair 간 대응점 자체는
   따로 계산해야 한다.
4. **§5.2 관측 count 확장** — 지금은 optimization 도중 계산되는 값이지만, view frustum
   교차만으로 초기화 시점에도 계산 가능하다(사전 신호로 재정의 가능).

이번 파일럿은 1번(opacity)만 시험했다 — 코드 추가 없이 기존 체크포인트만으로 되기 때문이다.

## 3. 핵심 기술적 난점 — densification이 인덱스를 깨뜨린다

C1-b는 기본적으로 densification을 켠 채로 돈다(§4.5 표의 모든 행). 실측 확인:

```
scene 0588138dfec165a1, 2-view: iter0 Gaussian 수 131072 → 60s 시점 189163
```

clone/split/prune를 거치므로 iter0의 몇 번 Gaussian이 60s의 몇 번이 됐는지 로그에 없다.
직접 `Δmeans = means_60s - means_0`을 할 수 없다.

**이번 파일럿이 쓴 근사**: iter0의 각 Gaussian을 60s 시점 점군에서 3D로 가장 가까운 점에
매칭(`scipy.spatial.cKDTree`, k=1)하고 그 거리를 이동량으로 삼는다. 이건 진짜 계보 추적이
아니다 — 특히 이동량이 큰 곳일수록 매칭 오차도 커질 수 있어, 상관관계의 크기(방향은 몰라도)는
과소·과대평가될 수 있다.

**깨끗한 방법**: `vanilla_3dgs_runner.py`에 이미 있는 `--densification off` 플래그로 C1-b를
다시 돌리면 Gaussian 개수가 고정되어 인덱스가 그대로 대응한다 — 직접 `Δmeans`를 계산할 수
있다. 소규모 GPU 작업(2-view 몇 scene이면 충분, C1-b 인프라 그대로 재사용)이 필요해 C2가
끝난 뒤로 미룬다.

## 4. 파일럿 결과 (재실행 0, `c4a_offtheshelf_uncertainty_pilot.py`)

RE10K C1-b 기존 체크포인트(2-view 17 scene + 4-view 20 scene = 37 scene)에서, iter0 opacity와
nearest-neighbor 이동 거리의 상관관계:

| 조건 | scene 수 | 음의 상관 비율 | 평균 상관계수 | 저-opacity 사분위 / 고-opacity 사분위 이동량 비 |
|---|---:|---:|---:|---:|
| RE10K 2-view | 17 | 15/17 (88%) | −0.16 | 약 2.0배 |
| RE10K 4-view | 20 | 18/20 (90%) | −0.07 | 약 2.9배 |
| **전체** | **37** | **33/37 (89%)** | **−0.107** | **2.63배** |

방향이 매우 일관적이다: **opacity가 낮은(모델이 암묵적으로 덜 확신하는) Gaussian일수록
refinement 중 더 많이 움직인다.** Diff3R의 학습된 Λ가 예측하는 방향과 같다.

## 5. 해석과 한계

**해석**: opacity라는, 학습 목적과 무관하게 이미 나오는 신호가 "여기가 나중에 많이 바뀔
곳"을 어느 정도 예고한다 — Diff3R가 굳이 별도 모듈을 학습한 이유가 "기성 신호로는 전혀 안
되기 때문"은 아닐 수 있다는 뜻이다. 다만 이게 "학습된 Λ를 대체할 수 있다"는 결론까지 가려면
아래 한계를 먼저 없애야 한다.

**한계**:
1. Nearest-neighbor 매칭은 근사다 — §3의 densification=off 재실행으로 확인 전까지는 상관관계의
   *크기*를 정량적 결론으로 쓰지 않는다(방향만 잠정적으로 신뢰).
2. Opacity가 낮은 Gaussian은 애초에 렌더링 기여도가 작아(반투명·거의 안 보이는 점) 그
   위치가 photometric loss에 거의 영향을 안 주므로, "많이 움직인다"가 "불확실해서 교정됐다"가
   아니라 "아무도 신경 안 써서 아무렇게나 표류했다"일 수도 있다 — 두 해석이 이 데이터만으로는
   분리되지 않는다. 저-opacity 영역의 이동이 실제로 test PSNR을 개선하는 방향인지 확인이
   필요하다(예: 저-opacity 영역만 masking하고 PSNR 기여도를 따로 계산).
3. 37 scene 전부 pooled, scene cluster bootstrap CI 미산출 — 통계적 유의성 주장 아님, 방향
   신호 확인 단계.
4. opacity 하나만 시험함. §2의 나머지 후보(cost volume variance, 기하 σ_depth)는 미시도.

## 6. 다음 단계

1. **(GPU 필요, C2 종료 후)** `--densification off`로 소규모 C1-b 재실행 — 인덱스 고정된
   직접 `Δmeans` 확인, 이번 파일럿의 근사 여부 검증.
2. 저-opacity 이동이 실제로 PSNR에 기여하는지 masking 분석(재실행 0, 위 한계 2 해소).
3. cost volume variance 신호 추가(코드 수정 필요, encoder hook).
4. 방향 신호가 densification=off에서도 재현되면 §5(결과)나 §6(가이드라인)에 탐색적 확장으로
   추가 검토 — ReSplat(§4.6)과 같은 패턴으로, 사전 등록 축에 섞지 않고 별도 절로 유지.
